# Project Memory — Keputusan Arsitektur

## Autentikasi (PENTING — jangan diubah)
- Login memakai tabel kustom **`admins`** (`username` + `password_hash` bcrypt) — **BUKAN** `auth.users` Supabase Auth.
- **Alasan:** project ini harus portabel dari Supabase ke Laragon/MySQL. Jangan pernah memigrasi ke Supabase Auth / `auth.users`.
- Skema lengkap: `schema.supabase.sql` (PostgreSQL / Supabase) dan `schema.mysql.sql` (MySQL / Laragon).
- **KONVENSI**: setiap perubahan di `schema.mysql.sql` WAJIB diterapkan juga ke `schema.supabase.sql` — alur & struktur tabel sama persis, hanya syntax disesuaikan per DB (AUTO_INCREMENT vs SERIAL, TIMESTAMP vs TIMESTAMPTZ, dll). **Tanpa `auth.users()`** di kedua file.
- **Migrasi**: folder `migrations/` berisi file SQL berpasangan `supabase/<NN>_*.sql` dan `mysql/<NN>_*.sql` dengan alur sama persis (konvensi yang sama seperti schema). Migrasi bersifat idempotent (ON CONFLICT DO NOTHING / ON DUPLICATE KEY UPDATE no-op) dan dijalankan SETELAH schema. Contoh: `migrations/supabase/01_seed_dummy_data.sql` ↔ `migrations/mysql/01_seed_dummy_data.sql` berisi seed lengkap 17 app + 51 tech + 16 kategori.
- **⚠️ Gotcha sequence id**: seed memakai id EKSPLISIT (1-17) yang TIDAK menggerakkan sequence (PostgreSQL) / AUTO_INCREMENT (MySQL). Tanpa sinkronisasi, INSERT baru menabrak id lama → error 500 `duplicate key value violates unique constraint "apps_pkey"`. Selalu sertakan `setval(...)` (Supabase) / `ALTER TABLE ... AUTO_INCREMENT = MAX(id)+1` (MySQL) di akhir migrasi apa pun yang memasukkan baris dengan id eksplisit. Perbaikan untuk DB yang sudah terlanjur: `migrations/supabase/03_fix_sequence_ids.sql` ↔ `migrations/mysql/03_fix_sequence_ids.sql`.
- Sesuai konvensi ini, API login/profile memakai `supabaseAdmin` (service role) di sisi server, dan `admins` di-protect RLS `service_role` di Supabase.
- **⚠️ Sesi (PENTING)**: cookie `admin_session` hanya memuat **token acak 256-bit** yang disimpan di tabel `sessions` (kolom `token`, `admin_id`, `expires_at` — 7 hari). Setiap permintaan API DIVALIDASI ke DB via `getSessionAdminId` di `src/lib/apps.ts` (async, `await` wajib). Format cookie lama `base64(id:timestamp)` **TIDAK diterima** (bisa dipalsukan tanpa kata sandi). Alur: login → `createSession(adminId)` + `setSessionCookie`; logout → `destroySession` + `clearSessionCookie`. Helper ada di `src/lib/apps.ts` (bukan di route).

## Data Aplikasi (Portal Direktori Aplikasi)
- Tabel inti selain `admins`: `sessions` (sesi login token acak), `categories`, `apps`, `app_tech` (teknologi per aplikasi), `settings` (key-value).
- Tipe `App` (lihat `src/types/index.ts`): `status` ∈ active/inactive/maintenance/deprecated, `env` ∈ production/staging/development, `progress` 0–100, `tech` array → disimpan di relasi `app_tech`.
- **Sumber data:** semua halaman (dashboard, apps, categories) fetch via `src/lib/apps.ts` (`getAllApps`/`getAllCategories`, memakai `cache()` React untuk dedupe per request). `src/data/initialData.ts` (APP_DATA) hanya **fallback** bila Supabase tidak terkonfigurasi / query gagal.
- **API apps:** `GET/POST /api/apps`, `PATCH/DELETE /api/apps/[id]`, `GET/POST /api/categories`, `PATCH/DELETE /api/categories/[name]` — semua butuh cookie `admin_session` (cek via `getSessionAdminId` di `src/lib/apps.ts`). POST membuat kategori otomatis bila nama kategori belum ada. Rename kategori (`PATCH`) otomatis mengubah nama kategori semua app (relasi via `category_id`); delete kategori membuat app-nya `Uncategorized` (FK `ON DELETE SET NULL`).
- **Realtime:** endpoint SSE `GET /api/realtime` (butuh `admin_session`) meneruskan event `postgres_changes` dari `supabaseAdmin` untuk tabel `apps`, `app_tech`, `categories`. Klien memakai `useRealtime` (`src/hooks/useRealtime.ts`) — event memicu refetch `GET /api/apps` + `GET /api/categories` + `GET /api/technologies`, plus polling cadangan 10 detik. Agar event terkirim, tabel wajib terdaftar di publikasi `supabase_realtime` (lihat `migrations/supabase/02_enable_realtime.sql`).
- **Teknologi (TANPA tabel registri):** daftar teknologi = `SELECT DISTINCT tech FROM app_tech` (`getAllTechnologies` di `src/lib/apps.ts`). Tech baru otomatis muncul begitu dipakai oleh sebuah aplikasi. API: `GET /api/technologies`, `PATCH/DELETE /api/technologies/[name]` (butuh `admin_session`; rename/delete langsung memodifikasi relasi `app_tech`). Halaman `/technologies` = browse + tambah + rename + hapus. Teknologi yang **ditambahkan dari halaman itu disimpan di localStorage** (`custom_technologies`, helper `src/lib/customTech.ts` — pola sama seperti `custom_categories`) karena belum ada barisnya di `app_tech`; ia muncul di pilihan form aplikasi (di-merge di `AppsPage`) dan otomatis berpindah ke database begitu dipakai sebuah aplikasi.
- **Form tambah/edit aplikasi** (`AddAppModal.tsx`): kategori memakai `<select>` dari data `categories`; tech stack memakai multi-select chip dari `getAllTechnologies` + input untuk menambah nama baru (langsung ikut tersimpan ke `app_tech`).
- **Log Aktivitas** (migrasi `06_add_activity_logs.sql`): tabel `activity_logs` (audit trail) mencatat siapa (admin_username) melakukan aksi apa (create/update/delete/import/reset) pada entitas apa (app/category/technology/system). Pencatatan dilakukan di route mutasi via `logActivity` (`src/lib/apps.ts`, best-effort); sesi diambil lengkap (id+username) lewat `getSessionAdmin` (bukan hanya `getSessionAdminId`). Halaman `/logs` + API `GET /api/logs` (filter action/entityType/search + pagination + total).
- Kategori & icon/gradient di halaman Kategori: nama kategori dari DB; pengaturan visual (icon/gradient) tetap localStorage `custom_categories`.

## Hidrasi React & Koeksistensi Ekstensi Browser (PENTING)
- **Aturan emas: jangan pernah baca `localStorage`/`window`/`document` saat render** (di luar `useEffect`/event handler). Server & client akan merender beda → error hidrasi + re-render penuh. Semua preferensi (tema, card view, notif read, custom categories/tech) WAJIB dibaca di `useEffect`, dipakai untuk render hanya setelah mount.
- **Jangan inisialisasi state dengan nilai non-deterministik** seperti `useState(() => Date.now())` — server & hidrasi beda beberapa ms → mismatch teks (mis. "baru saja" vs "1 menit lalu") di batas menit/jam. Pola aman: inisialisasi 0 lalu set di effect/fetch (lihat `Topbar`), ATAU tandai elemen teks-nya `suppressHydrationWarning` (lihat sel waktu di `LogsPage` — teks relatif waktu memang diizinkan beda).
- **Tema (anti-FOUC):** class `dark` di-set di `<html>` oleh inline script di `src/app/layout.tsx` (membaca `app_dark_mode` SEBELUM paint), bukan oleh React. Semua styling gelap memakai variant Tailwind `dark:` yang keyed ke `.dark` di `<html>` (lihat `@custom-variant dark` di `globals.css`) — jangan pernah menggantinya dengan class kondisional dari state (mis. `${isDark ? 'dark' : ''}` di wrapper), karena state baru berubah setelah mount → flash.
- **`suppressHydrationWarning` di `<html>`/`<body>` (`layout.tsx`):** wajib dipertahankan — ini yang membuat mutasi atribut dari luar (inline script tema, ekstensi yang menambah class/atribut sebelum hidrasi) tidak memicu error hidrasi.
- **Mount point ekstensi:** `<div id="ext-root">` di `layout.tsx` adalah satu-satunya tempat resmi ekstensi browser menyuntik node. Elemen ini statis & tak pernah di-render ulang React, jadi node yang disuntik setelah hidrasi bertahan. Ekstensi yang menyuntik ke `<main>`/list React akan merusak hidrasi (mismatch → React buang HTML SSR & re-render penuh, node ekstensi terhapus). Jika membuat fitur yang menampung node pihak ketiga, gunakan wadah di luar subtree yang re-render (jangan di dalam komponen ber-state).
- **Realtime/SSE** (`useRealtime`): polling cadangan 10 detik WAJIB dipertahankan — ekstensi/adblock bisa memblokir `fetch`/`EventSource`.
- Recharts `ResponsiveContainer` (`DashboardPage`) aman untuk SSR di v3 (render kontainer kosong sampai terukur di client); jangan downgrade/upgrade versi tanpa verifikasi hidrasi.
