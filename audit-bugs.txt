AUDIT BUGS & KESALAHAN SISTEM
Tanggal: 17 Agustus 2026
Proyek: next-app (Portal Direktori Aplikasi v2)

================================================================================
KRITIS
================================================================================

1. src/proxy.ts:24-32 — Middleware tidak memvalidasi sesi ke database
Tingkat: KRITIS

Penjelasan:
Proxy hanya memeriksa keberadaan cookie 'admin_session' tanpa memvalidasi token 
ke database. Cookie yang sudah expired, revoked, atau dipalsukan masih akan 
memberikan akses ke halaman. Ini berarti sesi yang sudah dilogout tetap bisa 
diakses, atau token curian bisa digunakan tanpa batas waktu efektif.

Saran Perbaikan:
Validasi token di middleware atau gunakan middleware Next.js yang memanggil 
'getSessionAdminId' dari src/lib/apps.ts untuk memastikan token masih valid 
dan belum expired.

--------------------------------------------------------------------------------

2. src/app/api/admin/data/route.ts:60-120 — Import data tanpa transaction
Tingkat: KRITIS

Penjelasan:
Proses import melakukan 'wipeData()' (menghapus semua data) lalu insert data 
baru tanpa transaction. Jika insert gagal di tengah proses (misalnya duplicate 
key, network error, atau timeout), database akan kosong dan tidak ada cara 
untuk rollback. Data hilang permanen.

Saran Perbaikan:
Bungkus seluruh operasi wipe+insert dalam database transaction, atau backup 
data terlebih dahulu sebelum wipe. Alternatifnya, gunakan atomic operation 
yang memastikan semua berhasil atau semua dibatalkan.

--------------------------------------------------------------------------------

3. src/app/api/login/route.ts:15 — Tidak ada rate limiting
Tingkat: KRITIS

Penjelasan:
Endpoint login tidak memiliki rate limiting atau account lockout mechanism. 
Attacker bisa melakukan brute force attack tanpa batas untuk menebak password 
admin.

Saran Perbaikan:
Tambahkan rate limiting (misalnya max 5 percobaan per IP per menit) dan/atau 
progressive delay setelah beberapa percobaan gagal. Bisa menggunakan Redis 
untuk tracking attempt per IP/username.

TINGGI

4. src/lib/apps.ts:168-182 — Race condition di createApp
Tingkat: TINGGI

Penjelasan:
'resolveCategoryId' melakukan SELECT lalu INSERT kategori tanpa transaction. 
Jika dua request membuat kategori dengan nama yang sama secara bersamaan, 
salah satu akan gagal dengan duplicate key error. Ini juga bisa menyebabkan 
kategori duplikat jika timing tepat.

Saran Perbaikan:
Gunakan database transaction atau constraint UNIQUE dengan 'ON CONFLICT DO 
NOTHING'. Alternatifnya, gunakan upsert (INSERT ... ON CONFLICT UPDATE) jika 
database mendukung.

--------------------------------------------------------------------------------

5. src/lib/apps.ts:345-353 — Session token tidak dirotasi
Tingkat: TINGGI

Penjelasan:
Token sesi tidak pernah dirotasi setelah login. Jika attacker mendapatkan 
token (misalnya via XSS), mereka bisa menggunakannya terus-menerus. Token juga 
tidak dirotasi setelah perubahan password, sehingga sesi lama tetap aktif.

Saran Perbaikan:
Rotasi token setiap N request atau setelah interval tertentu (misalnya setiap 
jam). Invalidate semua sesi saat password berubah. Tambahkan endpoint untuk 
melihat dan revoke sesi aktif.

--------------------------------------------------------------------------------

6. src/app/api/admin/data/route.ts:8-13 — wipeData tanpa atomicity
Tingkat: TINGGI

Penjelasan:
Jika salah satu DELETE di 'wipeData' gagal (misalnya table 'app_tech' gagal 
tapi 'apps' berhasil), database akan berada dalam state tidak konsisten. Data 
sebagian terhapus, sebagian tidak.

Saran Perbaikan:
Bungkus dalam transaction atau pastikan ada mekanisme rollback. Jika satu 
table gagal dihapus, batalkan semua operasi dan kembalikan ke state awal.

7. src/lib/validate.ts:75-77 — Validasi password lama tidak konsisten
Tingkat: SEDANG

Penjelasan:
'validatePasswordChange' memeriksa panjang password baru (min 6, max 72) tapi 
tidak memeriksa panjang password lama. Password lama yang terlalu pendek 
(misalnya dari bug migrasi lama) akan diterima, dan password lama yang terlalu 
panjang bisa menyebabkan masalah bcrypt.

Saran Perbaikan:
Tambahkan validasi panjang yang sama untuk 'currentPassword':
  if (currentPassword.length < LIMITS.passwordMin) {
    return { ok: false, error: 'Password saat ini terlalu pendek' }
  }
  if (currentPassword.length > LIMITS.passwordMax) {
    return { ok: false, error: 'Password saat ini terlalu panjang' }
  }

8. src/lib/apps.ts:277-280 — deleteApp tanpa validasi keberadaan
Tingkat: SEDANG

Penjelasan:
'deleteApp' langsung melakukan DELETE tanpa memeriksa apakah app tersebut ada. 
Di endpoint 'apps/[id]/route.ts:93-100', ini bisa menyebabkan log activity 
mencatat nama yang salah jika app tidak ditemukan.

Saran Perbaikan:
Periksa keberadaan app sebelum delete:
  const { data: existing } = await supabaseAdmin
    .from('apps')
    .select('id')
    .eq('id', id)
    .maybeSingle()
  if (!existing) throw new Error('APP_NOT_FOUND')

Atau handle error "not found" dengan lebih baik di level API route.

9. src/lib/apps.ts:447-448 — SQL injection potential di getActivityLogs
Tingkat: SEDANG

Penjelasan:
Meskipun Supabase menggunakan parameterized queries, 'ilike' dengan pattern 
'%${query.search}%' bisa bermasalah jika ada karakter khusus seperti '%' atau 
'_' dalam input user. Attacker bisa memanipulasi pencarian.

Saran Perbaikan:
Escape karakter khusus atau gunakan full-text search yang lebih aman:
  const escaped = query.search.replace(/[%_\\]/g, '\\$&')
  filtered = filtered.ilike('entity_name', `%${escaped}%`)

Atau gunakan operator yang lebih aman seperti 'eq' untuk exact match.

10. src/app/api/login/route.ts:41-42 — Timing attack masih memungkinkan
Tingkat: SEDANG

Penjelasan:
Meskipun ada DUMMY_HASH untuk menyamakan waktu bcrypt, waktu query database 
untuk mencari user yang ada vs tidak ada bisa berbeda signifikan. Attacker 
bisa mengukur perbedaan waktu ini untuk enumerasi username.

Saran Perbaikan:
Gunakan delay konstan setelah query database, terlepas dari apakah user 
ditemukan atau tidak:
  const startTime = Date.now()
  const { data, error } = await supabaseAdmin.from('admins')...
  const elapsed = Date.now() - startTime
  await new Promise(resolve => setTimeout(resolve, Math.max(0, 500 - elapsed)))

11. src/lib/apps.ts:295-300 — updateCategory/updateTechnology tanpa validasi
Tingkat: SEDANG

Penjelasan:
Fungsi 'updateCategory' dan 'updateTechnology' tidak memeriksa apakah entitas 
lama ada sebelum melakukan update. Ini bisa menyebabkan update yang tidak 
berpengaruh atau error yang tidak jelas.

Saran Perbaikan:
Periksa keberadaan entitas sebelum update:
  const { data: existing } = await supabaseAdmin
    .from('categories')
    .select('id')
    .eq('name', name)
    .maybeSingle()
  if (!existing) throw new Error('CATEGORY_NOT_FOUND')

Atau kembalikan informasi apakah update berhasil mempengaruhi baris.

12. src/lib/apps.ts:484-490 — Cookie SameSite=Lax bukan Strict
Tingkat: RENDAH

Penjelasan:
Cookie menggunakan 'sameSite: lax' yang masih memungkinkan beberapa CSRF 
attack scenarios (misalnya top-level navigation). 'lax' sudah cukup baik 
untuk kebanyakan kasus, tapi 'strict' lebih aman.

Saran Perbaikan:
Pertimbangkan 'sameSite: strict' jika tidak ada workflow yang membutuhkan 
cross-site navigation:
  response.cookies.set(SESSION_COOKIE, token, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'strict',
    maxAge: SESSION_DAYS * 24 * 60 * 60,
    path: '/',
  })

13. src/app/api/realtime/route.ts:52-60 — Channel cleanup tidak robust
Tingkat: RENDAH

Penjelasan:
Jika koneksi SSE terputus secara tidak normal (misalnya network error di 
server side), channel Supabase mungkin tidak dibersihkan dengan benar, 
menyebabkan resource leak.

Saran Perbaikan:
Tambahkan error handling yang lebih baik dan pastikan cleanup selalu terjadi:
  const stream = new ReadableStream<Uint8Array>({
    start(controller) {
      try {
        // setup channel...
      } catch (err) {
        controller.error(err)
      }
    },
    cancel() {
      try {
        if (heartbeat) {
          clearInterval(heartbeat)
          heartbeat = null
        }
        if (channel) {
          supabaseAdmin.removeChannel(channel)
          channel = null
        }
      } catch (err) {
        console.error('[realtime] Error during cleanup:', err)
      }
    },
  })

14. src/lib/validate.ts:107-111 — Validasi URL tidak konsisten
Tingkat: RENDAH

Penjelasan:
Di 'validate.ts', 'isHttpUrl' digunakan untuk validasi tapi URL tetap dipotong 
dengan 'cleanString' sebelum validasi. Ini bisa menyebabkan URL yang dipotong 
menjadi invalid tapi lolos validasi.

Saran Perbaikan:
Validasi URL setelah dipotong, atau potong hanya jika valid:
  const url = cleanString(body.url, LIMITS.url)
  if (url && url !== '#' && !isHttpUrl(url)) {
    return { ok: false, error: 'URL harus diawali http:// atau https://' }
  }
  // url sekarang sudah divalidasi

Atau validasi URL sebelum dipotong dan tolak jika terlalu panjang:
  const rawUrl = isString(body.url) ? body.url.trim() : ''
  if (rawUrl && rawUrl !== '#' && !isHttpUrl(rawUrl)) {
    return { ok: false, error: 'URL harus diawali http:// atau https://' }
  }
  if (rawUrl.length > LIMITS.url) {
    return { ok: false, error: `URL maksimal ${LIMITS.url} karakter` }
  }
